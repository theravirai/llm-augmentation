# Output Reports, Logs & Result Interpretation Guide

This document describes the structure of output artifacts generated by the framework, the JSON and Markdown reporting schemas, and how to interpret experimental findings for scientific publications and the master thesis defense.

---

## 1. Output Directory Layout & Naming Conventions

All evaluation logs, traces, and reports are filed into dedicated semantic subdirectories under `results/`:

```text
results/
├── comparisons/
│   └── <task_id>/
│       ├── <task_id>_condition_comparison.md      # Side-by-side three-condition comparison matrix
│       ├── <task_id>_cond_A_report.md             # Human-readable Condition A report
│       ├── <task_id>_cond_A_eval.json             # Machine-readable Condition A metrics
│       ├── <task_id>_cond_A_trace.json            # Step-by-step turn trajectory & prompt snapshots
│       ├── <task_id>_cond_B_report.md
│       ├── <task_id>_cond_B_eval.json
│       ├── <task_id>_cond_B_trace.json
│       ├── <task_id>_cond_C_report.md
│       ├── <task_id>_cond_C_eval.json
│       └── <task_id>_cond_C_trace.json
│
├── single_runs/
│   └── cond_<condition>/
│       └── <task_id>/
│           ├── <task_id>_cond_<condition>_report.md
│           ├── <task_id>_cond_<condition>_eval.json
│           └── <task_id>_cond_<condition>_trace.json
│
├── benchmarks/
│   └── <dataset_name>/
│       └── cond_<condition>/
│           ├── <dataset_name>_cond_<condition>_summary.md
│           └── <dataset_name>_cond_<condition>_summary.json
│
└── archive/                                       # Legacy exploratory experiment archives
```

## 4. Interpreting Results for the Master Thesis

### 4.1 Addressing RQ1: Effectiveness of Static Fact Augmentation
* **Condition A (Baseline):** Identifies the limits of textual search. When a bug spans multiple decoupled files (e.g. `Gson.java` overriding adapters defined in `TypeAdapters.java`), models relying on source code alone consistently miss the factory file (`file_recall = 50%`, `exact_file_match = false`).
* **Condition B (Precomputed AOT):** Shows whether **Confirmation Bias** occurs. In cases like Gson #2158, models provided with precomputed static summaries often dismiss facts showing `Gson$1` because their linguistic prior firmly associates all adapters with `TypeAdapters.java`.
* **Condition C (Active MCP):** Demonstrates that active query-response loops overcome confirmation bias. When the agent queries `sootup_find_allocations` dynamically, it immediately receives concrete line-level proof of instantiation in `Gson.java`, achieving 100% gold patch parity.

### 4.2 Addressing RQ2: Cost-Benefit Analysis
* **Token Budget:** Compare `total_tokens` between Condition B and Condition C. Condition B incurs high token costs on every query because static summaries are dumped upfront. Condition C consumes tokens selectively only when the agent decides to invoke a tool.
* **Tool Calling Precision:** In Condition C logs, check `tool_calls_trace`. Evaluate whether the agent invoked the necessary primitives (`hierarchy`, `find-allocations`) or called irrelevant tools.
* **Compilation Impact:** Observe `compilation_status`. If certain tasks could not compile due to build-tool incompatibilities, report the exclusion rate as defended in the thesis methodology (Slide 31).
